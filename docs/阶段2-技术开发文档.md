# 第 2 阶段技术开发文档｜热点事件 + 可信度 + 通用日报生成

> 配套文档：《微蓝日报 PRD》、《AI 产品 Vibe Coding 通用技术栈手册》、《技术适配声明》。
> 本文档只覆盖第 2 阶段。

## 一、阶段目标

对齐 PRD「一周 MVP 交付计划」的 **Day 3**，以及功能需求 **FR-03（事件聚类部分）、FR-04、FR-05、FR-06**。

- **交付范围**：
  1. 数据模型：热点事件（HotEvent）、事件证据（EventEvidence）、通用日报（DailyReport）、选题建议（TopicRecommendation）、热点速览（HotBrief）、生成任务（Job）。
  2. 事件提取：把近期来源条目用 LLM 聚成「热点事件」，并保留证据分组。
  3. 可信度标签：按 FR-05 规则**确定性计算**（官方确认 / 多方报道 / 早期信号）。
  4. 价值排序：按 FR-04 维度评分并排序，保留可解释理由。
  5. 通用日报生成：LLM 生成「3 个选题建议 + 5-7 条热点速览 + 一句话摘要」。
  6. 最小验收界面：手动触发提取/生成、查看事件与日报。
- **阶段产物**：能「触发 → 提取事件 → 生成日报 → 在网页看到日报」的后端能力。
- **明确不做**：公开网站（阶段 3）、用户账户/画像/个性化（阶段 4）、创作方案/反馈/邮件/订阅（阶段 5）、正式前端。
- **本阶段打通的主链路**：`来源条目 → LLM 提取热点事件 → 确定性可信度 → 排序 → LLM 生成日报 → 网页可查看`。

## 二、技术适配摘要

- 采用：FastAPI、Pydantic、SQLAlchemy、pytest（已有）。
- 启用：LLM 调用层（DeepSeek，OpenAI 兼容接口）+ 提交/轮询任务（后台线程 + 持久化 Job 表）。
- 暂缓：正式前端（阶段 3，届时用《前端技术栈手册》）；个性化（阶段 4）。
- 开发路径：后端先行 + 最小验收界面。

## 三、技术栈与模型

- **模型：DeepSeek（`deepseek-chat`），走 OpenAI 兼容接口。**
- `base_url` / `model_name` / `api_key` 全部从 `.env` 读取，**可切换火山方舟或 DeepSeek 官方**，代码不硬编码。
- **mock 模式**：无 Key 时返回确定性模拟输出，供开发、测试、界面验收；真实 Key 到位后同一接口直接切换。
- 结构化输出：模型输出 JSON → 后端确定性解析 → Pydantic 强校验；失败有限重试。

### 状态机

- 事件：`candidate → selected / brief / archived`（入选主选题 / 进入速览 / 归档）。
- 日报：`draft → published`（阶段 2 生成后为 draft，质检在阶段 6）。
- 任务：`pending → running → success | failed`，可恢复（持久化）。

### 关键规则（确定性代码，不依赖模型）

- **可信度**（FR-05）：
  - 证据含 ≥1 个 `official` 信息源 → `official`；
  - 否则证据来自 ≥2 个不同信息源 → `multi_source`；
  - 否则单一非官方来源 → `early_signal`。
- **排序分**（FR-04，临时方案 + 可配置，交付清单标注待冻结）：
  `sort_score = 0.3*relevance + 0.25*actionability + 0.2*freshness + 0.25*credibility_bonus`，理由文本随事件保存。

## 七、API / 工具设计

| 方法 | 路径 | 说明 | 长耗时 |
|---|---|---|---|
| POST | `/api/v1/events/extract` | 触发事件提取，返回 job id | 是（提交+轮询） |
| GET | `/api/v1/events` | 列出热点事件（含可信度、证据数） | 否 |
| GET | `/api/v1/events/{id}` | 事件详情（含证据条目） | 否 |
| POST | `/api/v1/reports/generate` | 生成今日日报，返回 job id | 是（提交+轮询） |
| GET | `/api/v1/reports` | 列出日报 | 否 |
| GET | `/api/v1/reports/{id}` | 日报详情（选题+速览+证据链接） | 否 |
| GET | `/api/v1/jobs/{id}` | 查询任务状态 | 否 |

- 长耗时接口：**提交 + 轮询**。POST 立即返回 `{job_id}`，后台线程执行；客户端轮询 `GET /jobs/{id}` 直到 success/failed。
- 任务结果持久化，进程重启后可恢复查询（但本阶段不自动续跑中断任务）。

## 八、Prompt 设计

### event_extraction.md（事件提取）

- 角色：把来源条目聚成候选热点事件。
- 输入：近 48 小时、按来源去重后最多 150 条的条目（id、标题、来源名、URL、时间、摘要）。
- 输出 JSON：`{"events":[{"title","summary","evidence_item_ids":[...],"relevance_score":1-5,"actionability_score":1-5,"reason"}]}`。
- 约束：不得编造条目中不存在的事实；证据必须用给出的 item id；正反例说明格式。

### report_generation.md（日报生成）

- 角色：基于已排序事件生成通用日报。
- 输入：已选事件的标题、摘要、可信度、证据链接、排序理由。
- 输出 JSON：`{"summary","topics":[{"event_id","title","what_happened","why_now","angle","hook","structure","visual","time_window"}],"briefs":[{"event_id","summary"}]}`。
- 约束：只从给定事件取材；3 个选题、5-7 条速览；不生成完整逐字稿；保留证据链接。

## 十、测试要求

### 第一层 mock 测试（离线）

1. LLM 结构化输出解析器：合法 JSON、缺字段、超量、错误编号 → 校验/重试/报错。
2. 可信度确定性计算：三种标签各覆盖（含边界：两个非官方源=多方报道）。
3. 排序公式：分数计算与排序稳定性。
4. 事件提取编排：mock LLM 输出 → 事件+证据正确入库。
5. 日报生成编排：mock LLM 输出 → 选题/速览正确入库。
6. 任务状态机：pending→running→success/failed；失败可查询。
7. 事件去重：同一来源条目不被重复建证据。

### 第二层真实冒烟（阶段验收前，需真实 Key）

- 用真实 DeepSeek 跑通：`真实条目 → 提取事件 → 生成日报 → 网页可查看`。
- 记录：模型、耗时、Token 用量、首测结构合规率、重试次数、内容质量（人工判断）。

## 十二、风险与待确认项

- **模型成本**：事件提取 + 日报生成为**批量调用**（不是逐条），MVP 阶段成本极低。
- **聚类质量**：LLM 聚类是"临时方案"，阶段 6 用真实数据演练时统一评测质量阈值。
- **排序公式未冻结**：按手册"临时方案 + 显式标注 + 可配置"处理，交付清单标注待冻结。
- **需要产品经理决定的问题**：无（模型 Key 验收前提供即可）。
