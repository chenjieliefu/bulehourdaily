# 技术适配声明

> 依据《AI 产品 Vibe Coding 通用技术栈手册》第六节输出。
> 本声明只描述「微蓝日报」的技术适配结论，业务以 PRD 为准。

## 1. 产品形态判断

- **产品类型与核心任务**：内容策展 + AI 生成的日报产品。系统定时采集海外 AI 信息源，聚类成热点事件，生成通用日报与个性化日报（3 个抖音选题），并支持展开创作方案与发布反馈。
- **核心交互**：**一次生成 + 用户查看/反馈**。后台定时批量生成，创作者每天查看日报、展开方案、提交反馈；运营者每天做轻量质检。不是实时多轮对话，也不是画布/音视频时间轴类交互。
- **开发路径**：**后端先行**。产品可行性取决于「采集 → 聚类 → 选题生成」的质量，而不是交互本身。但日报文案质量需要"用眼睛看"才能验收，因此每个阶段配**最小验收界面（单个 HTML，挂在后端 static/）**；正式前端（Next.js）在核心链路验证通过后再做。
- **当前阶段范围**：阶段一 = 项目骨架 + 数据模型 + 固定信息源池 + 定时采集 + 来源条目与确定性去重。

## 2. 采用的默认方案

| 方案 | 采用原因 |
|---|---|
| Python 3.11.9 | 手册默认 3.11.x；已安装 3.11.9（本机原有 3.9 过旧） |
| FastAPI | 把后端能力做成可独立测试、可验收的 API |
| Pydantic | 校验接口输入输出 + 校验模型结构化输出 |
| pytest | mock 自动化测试，覆盖业务逻辑与解析器 |
| Git | 代码管理与可恢复（已初始化仓库） |
| 模型 = DeepSeek（经火山方舟 OpenAI 兼容接口） | 与产品经理确认；中文生成质量好、成本低；开发期先用 mock，验收前提供 Key |

## 3. 触发的按需模块

| 模块 | 触发需求 | 当前阶段是否引入 |
|---|---|---|
| SQLite + SQLAlchemy + Alembic | 信息源、来源条目、热点事件、日报、用户、画像、反馈等多实体关系 + 事务 | 阶段一引入（数据模型是本阶段核心） |
| 定时采集 | 每 30–60 分钟增量采集 | 阶段一用**进程内调度 + 手动触发**，先不上消息队列 |
| 异步任务接口 | 日报/方案生成是 LLM 长耗时任务 | 阶段二起用「提交任务 + 轮询状态」，暂不用 SSE |
| 邮件 | 个性化日报邮件送达 | 阶段五先用**本地模拟发送**，上线前再选供应商 |
| 正式前端 Next.js | Web 日报页面 | 核心链路验证通过后再引入（阶段三之后） |

## 4. 偏离或暂缓的默认方案

| 默认方案 | 替代/暂缓 | 原因 | 影响 | 重新评估条件 |
|---|---|---|---|---|
| X（推特）数据采集 | 开发期用官方免费源（RSS/博客/GitHub）+ 模拟数据 | X 官方接口昂贵、第三方抓取有合规风险；已与产品经理确认 | 开发期看不到真实 X 数据 | **商业上线前必须接入真实 X 采集（稳定性/成本/合规审查），已记入决策备忘，不会遗忘** |
| Node 22 LTS | 使用本机 Node 24 | 环境已装 24，版本更新、兼容 | 无实质影响 | 前端阶段如遇兼容问题再调整 |
| 生产数据库 PostgreSQL | 先用 SQLite | MVP 单机、低并发 | 后续迁移需一次数据迁移 | 用户量/并发/数据价值提升后 |
| 自动支付 | 人工确认付款 | PRD 已定，MVP 不做自动支付 | 运营手动操作 | 公开商业推广前 |

## 5. 强制底线检查

- **密钥与隐私**：通过。Key 只放 `.env`（已加入 `.gitignore`），不回显、不提交、不进前端。
- **数据与任务可恢复**：通过。SQLite 持久化 + Alembic 迁移；长任务状态持久化。
- **输入输出校验**：通过。Pydantic 强校验 + 统一错误格式；模型输出确定性解析。
- **错误与日志边界**：通过。统一错误响应，不向用户暴露堆栈；外部来源正文按不可信输入处理。
- **测试与真实模型验收**：计划 = 双层测试。第一层 pytest mock（离线可跑）；第二层真实 DeepSeek 端到端冒烟（阶段验收前，需真实 Key）。

## 6. 需要产品经理决定的问题

- 无（范围、交付形态、X 采集、模型均已确认）。
- 说明项（无需决定）：MVP 阶段 DeepSeek 成本极低（每日批量生成，量小）；邮件供应商、品牌域名、自动支付等按 PRD 开放项，上线前再对齐。
